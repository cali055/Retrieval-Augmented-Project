# Agentic RAG with LangGraph

An agentic Retrieval-Augmented Generation (RAG) system for answering questions using research papers indexed from arXiv.

This project extends a traditional RAG pipeline with an adaptive workflow built using **LangGraph**. Instead of always retrieving documents and generating an answer, the agent evaluates the query, retrieves relevant papers, grades the retrieved context, and can rewrite the query when the retrieved documents are not sufficiently relevant.

## What This Project Demonstrates

- Agentic RAG workflow orchestration with **LangGraph**
- Hybrid document retrieval using **OpenSearch**
- Semantic embeddings using **Jina AI**
- Local LLM inference using **Ollama**
- Query guardrails and document relevance grading
- Iterative query rewriting and retrieval
- Observability and tracing with **Langfuse**
- Docker-based development and service orchestration

## Key Features

### Agentic RAG Workflow

Unlike a traditional RAG pipeline that always retrieves documents, this implementation uses **LangGraph** to make retrieval decisions dynamically:

```text
User Query
    ↓
Guardrail Validation
    ↓
┌───────────────────────┐
│ Is query in scope?    │
└───────────────────────┘
    ↓ Yes
Retrieve Documents
    ↓
Grade Documents
    ↓
┌─────────────────────────────┐
│ Are retrieved documents     │
│ relevant to the query?      │
└─────────────────────────────┘
    ↓ Yes                 ↓ No
Generate Answer       Rewrite Query
                          ↓
                    Retrieve Again
```

### Guardrail Validation

Before retrieval, the agent evaluates whether the query falls within the supported research domain. Queries that pass the guardrail continue to document retrieval, while out-of-scope queries are handled without performing a search. This project currently uses an LLM to evaluate and score queries. In future iterations, deterministic verifiers could be explored to reduce reliance on LLM-based judgment.
### Document Retrieval

The retrieval layer uses **OpenSearch** with hybrid search, combining BM25 keyword retrieval with semantic vector search using embeddings generated by **Jina AI**.

### Query Rewriting

When the retrieved documents are not sufficiently relevant, an LLM rewrites the query to improve the next retrieval attempt. The workflow supports a maximum of two retrieval attempts.

### Answer Generation

Once relevant context is identified, the system generates the final answer using the retrieved research-paper context and a locally hosted **Ollama** model.

### Observability

The workflow integrates **Langfuse** for tracing and observability, allowing the execution of individual stages of the agentic RAG pipeline to be inspected.

## Architecture

The workflow is implemented as a **LangGraph StateGraph** with dedicated nodes for guardrail validation, retrieval, document grading, query rewriting, and answer generation.

```text
START
  │
  ▼
Guardrail
  │
  ├── Out of Scope ──→ END
  │
  ▼
Retrieve
  │
  ▼
Tool: retrieve_papers
  │
  ▼
Grade Documents
  │
  ├── Relevant ──→ Generate Answer ──→ END
  │
  └── Not Relevant
           │
           ▼
      Rewrite Query
           │
           ▼
        Retrieve
```

## Response Metadata

The agent returns additional metadata describing the workflow execution:

- `reasoning_steps` — high-level steps taken during execution
- `retrieval_attempts` — number of retrieval attempts performed
- `rewritten_query` — rewritten query when refinement occurs
- `sources` — relevant research-paper sources returned by the workflow

## Configuration

The workflow can be configured through `GraphConfig`:

| Configuration | Default |
|---|---|
| `max_retrieval_attempts` | `2` |
| `guardrail_threshold` | `60` |
| `model` | `llama3.2:1b` |
| `temperature` | `0.0` |
| `top_k` | `3` |
| `use_hybrid` | `true` |

## Prerequisites

### Environment Variables

Copy the example environment file:

```bash
cp .env.example .env
```

Configure the required values in `.env`:

- `JINA_API_KEY` — API key for Jina AI embeddings
- `LANGFUSE_PUBLIC_KEY` — Langfuse public API key
- `LANGFUSE_SECRET_KEY` — Langfuse secret API key

Langfuse is optional. If the Langfuse keys are not configured, tracing is disabled while the RAG pipeline can still run.

### Ollama

The project uses Ollama for local LLM inference.

Pull the configured model if required:

```bash
docker exec rag-ollama ollama pull llama3.2:1b
```

Verify that the model is available:

```bash
docker exec rag-ollama ollama list
```

### Start the Services

Start the complete Docker environment:

```bash
docker compose up --build -d
```

Main service endpoints:

- FastAPI: `http://localhost:8000/docs`
- OpenSearch: `http://localhost:9200`
- Ollama: `http://localhost:11434`
- Langfuse: `http://localhost:3001`

### Langfuse

For a self-hosted Langfuse setup:

```bash
docker compose up langfuse-web langfuse-worker langfuse-postgres langfuse-redis langfuse-minio clickhouse -d
```

Open `http://localhost:3001`, create an account, and configure the Langfuse API keys in `.env`.
